# 流式 Markdown Table 优化思路总结

## 背景与问题

当前问答流式输出来自 LLM token 流。token 的切分是随机的，而 Markdown table 是强结构（行、分隔行、列对齐）。  
如果后端把 token 原样透传，常见问题包括：

- 表格行被拆碎，前端渲染抖动或短暂错位
- 分隔行（`|---|---|`）不完整导致 table 无法识别
- 同一段内容“先错误渲染再修正”，用户体验不稳定
- 渲染责任完全压在前端，后端不可控、不可观测

核心结论：**不能把结构化渲染正确性完全交给前端容错。**

---

## 优化目标

本次优化目标是“在不破坏现有协议兼容性前提下，提高 table 输出稳定性”：

- 后端控制输出粒度，减少 table 半结构状态
- 保持现有 SSE 事件类型（`type=token`）不变
- 为未来协议升级（语义块事件）预留扩展空间
- 提供运行模式开关，支持灰度与回退

---

## 方案设计

### 1) 在后端引入流式输出处理层

新增 `backend/agent/output_processor.py`，在 `llm.astream()` 和 SSE 下发之间增加 `StreamMarkdownProcessor`：

- 输入：模型增量 token
- 处理：缓冲、分行、table block 识别与规范化
- 输出：可安全下发的文本片段（仍是字符串）

这层将“渲染稳定性”前置到后端，而不是后置到前端。

### 2) 三种输出模式（可配置）

通过 `TABLE_STREAM_MODE` 控制：

- `raw`：原样 token 直出（低延迟，高风险）
- `line`：按完整行输出（中等稳定）
- `block`：按表格块输出并规范化（默认推荐）

默认采用 `block`，在稳定性和实现复杂度之间取得平衡。

### 3) Table block 策略

在 `block` 模式下，处理器采用“行缓冲 + 表格块冲刷”：

- 先将 token 聚合为完整行
- 遇到疑似 table 行进入 table 缓冲区
- 在边界（空行或非 table 行）时统一冲刷
- 冲刷前进行基础规范化（见下）

这样可避免“半行/半表格”被前端提前渲染。

### 4) 表格规范化策略（基础版）

`_normalize_table_lines` 主要做：

- 自动补分隔行（若缺失）
- 统一列数（不足补空，超出截断）
- 行格式标准化（统一 `| col |` 形式）

目标是容错常见脏格式，降低前端渲染失败概率。

## 为什么这是更工程化的方向

- **后端可控**：输出边界由后端定义，不依赖前端猜测
- **兼容成本低**：SSE 事件类型不变，前端无需一次性重构
- **灰度友好**：通过环境变量可切模式，支持回退
- **可演进**：可进一步升级为语义块协议（table/code/paragraph）

---

## 当前方案边界（已知）

当前实现已明显提升稳定性，但仍有边界：

- table 识别规则偏启发式，复杂嵌套 Markdown 仍可能误判
- 单元格内复杂转义（如 `\|`）处理仍可继续增强
- 仍是文本流协议，前端无法直接拿到“结构化表格对象”

这些属于下一阶段优化内容。

---

## 下一阶段建议（工业级增强）

建议按以下顺序演进：

1. **协议升级为语义块事件**
   - 新增 `block_start/block_delta/block_end`
   - block kind：`table/paragraph/code`

2. **增强校验与降级**
   - 表格验证失败时自动降级为 code block 或纯文本
   - 记录 `invalid_reason` 便于排障

3. **可观测性建设**
   - 增加指标：table blocks、repair 次数、fallback 次数、输出延迟
   - 加入 request_id / conversation_id 关联日志

4. **测试体系完善**
   - 随机切片回归测试（模拟 token 随机断裂）
   - table 正常/异常用例集
   - SSE 契约测试

---

## 总结

这次优化的核心思路是：  
**把“Markdown table 渲染稳定性”从前端兼容问题，提升为后端输出质量控制问题。**

先通过“行级与块级控制 + 基础规范化”获得高收益，再逐步演进到语义块协议与可观测体系，最终达到工业级流式输出能力。
