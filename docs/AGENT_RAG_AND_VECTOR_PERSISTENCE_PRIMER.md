# Agent、RAG 与向量持久化：初学者导读

本文总结「Day 1 把内存向量库换成 FAISS 落盘」在**产品上的作用**，以及它和 **AI Agent 开发**各自对应哪一块能力。可与 [day-01.md](./day-01.md) 对照阅读。

---

## 一页纸总结

| 问题 | 答案 |
|------|------|
| **这次改了什么？** | 向量索引从「只存在进程内存」改为 **FAISS + 元数据落盘**；上传后写入磁盘，**重启后端仍可检索**，一般不必重新上传。 |
| **没改什么？** | LangGraph 的 **Agent 编排**、**工具调用协议**、`search_docs` 与 multi-query / rerank 的**检索流水线逻辑**基本不变；换的是「向量存在哪」。 |
| **算学了 Agent 的哪部分？** | **直接强化的是 RAG 数据层与工程化**（持久化、路径、嵌入一致性、异步里避免阻塞）。**Agent 本身**（何时调工具、图怎么循环）你仍在原代码里学，但这次提交主要动的是它脚下的**知识库地基**。 |
| **类比** | Agent 仍是「会查书的助手」；以前是「书页贴在易擦的黑板上」，现在是「书页抄进带目录的笔记本里」，**关机再开还在**。 |

## 1. 三个概念：大模型、RAG、Agent

### 大模型（LLM）

擅长理解与生成自然语言，但**不天然包含你私有的 PDF/Word 全文**，也**不会自动记住**你昨天上传的文件（除非每次把全文塞进对话，成本高、上下文也有限）。

### RAG（检索增强生成）

流程可以记成一句话：**先从你自己的文档里搜出相关片段，再把这些片段交给大模型，让它基于材料回答。**  
这样回答更贴文档，也有利于减少「凭空编造」（仍要注意幻觉，但比纯靠模型好得多）。

### Agent（本项目语境：带工具的对话系统）

不只做「一问一答」，而是模型可以**决定要不要调用工具**（例如「去知识库里搜一下」），根据工具返回结果再继续推理、继续输出，并可多轮。  
本仓库用 **LangGraph** 把「模型 → 是否调工具 → 执行工具 → 再回到模型」画成一张**状态图**，按边自动循环直到结束。

## 2. 向量与向量库（生活类比）

把文档切成很多小段（**chunk**），每段变成一串数字（**向量 / embedding**）。语义相近的段落，在向量空间里距离更近，于是「搜索」变成「算和用户问题最像的几段」。

- **改之前（内存向量库）**：索引在**进程内存**里，进程结束或后端重启，索引就像从桌上收走，**要重新上传、重新建库**。
- **改之后（FAISS 落盘）**：向量和必要元数据**写到硬盘**（如 `index.faiss` 与 `store_meta.json`），**重启服务后仍在**，问答仍可命中历史文档。

---

## 3. 与本项目数据流的关系（改在哪一环）

典型路径如下（与本次改动的关系已标注）：

1. **上传**：解析文件 → 分块 → 嵌入 → **写入向量库**（**此处变为落盘持久化**）。
2. **聊天**：LangGraph Agent 判断是否需要依据文档。
3. **工具 `search_docs`**：multi-query、向量相似度检索、rerank 等，从向量库取片段。
4. **模型**：结合检索结果生成最终回答（含流式等）。

因此：**持久化解决的是第 1 步与第 3 步之间的「库是否长期存在」**；**第 2、4 步的 Agent 行为**不是这次提交的重点。

## 4. 学习地图：Agent 编排 vs RAG 工程

| 方向 | 内容 | 与本次改动的关系 |
|------|------|------------------|
| **Agent 编排** | 系统提示、工具描述、`bind_tools`、LangGraph 节点与边、何时结束循环 | 代码主体未因持久化而重写；仍是你理解 Agent 的核心入口。 |
| **RAG 与数据层** | 分块、嵌入、向量索引、检索与 rerank、索引与嵌入维度/后端一致性 | **本次改动落在这里**：尤其是**持久化**与**可部署性**。 |
| **Web 与异步** | FastAPI 路由、依赖注入、避免长时间阻塞事件循环（如 `asyncio.to_thread`） | 上传入库路径上做了与阻塞相关的工程处理。 |

一句话：**Agent 学的是「会不会查、会不会用工具」；持久化学的是「查的那座库在重启后还在不在」。** 两者在真实产品里通常要一起过关。

## 6. 建议的下一步（读代码顺序）

在不改代码的前提下，可按下面顺序对照仓库阅读，把「Agent」与「RAG 地基」串起来：

1. `backend/app/main.py`：上传与 `/chat`、`/health` 如何拿到向量库。
2. `backend/app/deps.py`：向量库单例如何创建、索引目录从哪来（含环境变量 `RAG_FAISS_INDEX_DIR`）。
3. `backend/agent/graph.py`：图的结构（模型与工具的循环）。
4. `backend/agent/tools.py`：`search_docs` 如何调用检索。
5. `backend/kb_rag/retrieval.py`：multi-query + 向量检索 + rerank。
6. `backend/kb_rag/faiss_store.py`：落盘格式、加载与校验（维度与 `embedding_backend` 不一致时会丢弃损坏索引，需重新上传）。

## 8. 续：三句话速记（复习用）

1. **RAG**：不指望模型「背下」整份文档，而是**先检索片段，再让模型根据片段说话**。  
2. **Agent**：模型可以**自己决定要不要调用 `search_docs`**，LangGraph 负责把「想 → 调工具 → 再想」循环跑完。  
3. **Day 1 持久化**：检索仍走同一条流水线，但向量从**内存**换成**磁盘 FAISS**，所以**重启服务后知识库还在**。

---

## 9. 续：常见误区（初学者易混）

| 误区 | 实际情况 |
|------|----------|
| 「做了持久化 = 学会了 Agent」 | 持久化主要解决 **数据层**；Agent 的编排、提示词、工具设计仍要单独学。 |
| 「模型读过上传文件」 | 模型通常**没有**整份文件在权重里；是你把文件**切块、向量化、检索**后，把**片段**塞进对话里。 |
| 「FAISS = 大模型的一部分」 | FAISS 是**向量检索引擎**（类似本地搜索引擎），和 GPT/DeepSeek 等 **LLM 是不同组件**。 |
| 「换嵌入模型不用管旧索引」 | 维度和向量空间会变；本仓库会在**后端/嵌入不一致**时**拒绝加载旧索引**，需要**重新上传**建库。 |
| 「`search_docs` 一定会被调用」 | 由**模型根据对话与工具描述**决定；可通过系统提示引导「涉及文档事实时要先检索」。 |

## 10. 续：迷你术语表

| 术语 | 一句话 |
|------|--------|
| **Chunk** | 文档切成的短文本块，便于嵌入与检索。 |
| **Embedding / 向量** | 文本的数值表示，语义相近的文本向量往往更接近。 |
| **向量库 / 索引** | 存很多向量（及与 chunk 的对应关系），支持「按相似度找 Top-K」。 |
| **FAISS** | Meta 开源的向量相似度检索库；本项目用来**落盘**并加速检索。 |
| **Tool / 工具** | 模型可调用的函数；这里典型工具是 **`search_docs`**。 |
| **LangGraph** | 用**图**描述 Agent 多步流程（节点、边、状态），本仓库里负责 agent ↔ tools 循环。 |
| **`asyncio.to_thread`** | 把**耗时的同步代码**放到线程里跑，减轻 FastAPI **事件循环被卡住**的问题（如重嵌入、写索引）。 |

## 11. 续：和后续学习日怎么接（鸟瞰）

- **Day 1（当前）**：索引能**活下来**（持久化）。  
- **Day 2 及以后**（见 [STUDY_PLAN_7_DAYS.md](./STUDY_PLAN_7_DAYS.md)）：在「库还在」的前提下，再做**多索引管理、检索策略、LangSmith、更复杂的图**等，才有意义。

把 Day 1 想成：**先有一个不会一重启就空的「书架」**，再往书架上加分类、借还规则、观测与评测。
